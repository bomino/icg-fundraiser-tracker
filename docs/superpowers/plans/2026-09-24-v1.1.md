# ICG Fundraiser Tracker v1.1 — Implementation Plan

> **For agentic workers:** executed with superpowers:subagent-driven-development. Each task ends with `npm run check` green and one commit on branch `feat/v1.1`.

**Goal:** a small, client-side v1.1. It needs no `apps-script/Code.gs` change and no new Google permissions.
- faster payment entry from a donor
- list filters and a follow-up list
- a "possible duplicate payments" health check
- a Friday projector display that never prompts for sign-in
- the parked review fixes, installability without a service worker, a performance check, a CI smoke test, and docs

**Rationale and scope decisions:** see the critical review in the approved plan, summarised in the Global Constraints below.

**Spec lineage:** `docs/superpowers/specs/2026-09-23-fundraiser-web-app-design.md` (v1) and `DESIGN.md` (visual; includes the Friday display description).

## Global Constraints

- **No changes to `apps-script/Code.gs` or `apps-script/appsscript.json`** in this release; everything is client-side. `web/src/demo.ts` stays in step with any `Api` usage.
- Keep the Excel parity exact: `test/engine/parity.test.ts` must pass unchanged. New app-only health checks are not part of the parity mapping.
- Reuse existing modules (see each task). No new runtime dependencies except `@playwright/test` as a dev dependency in Task 8.
- The v1 global constraints still apply (from `docs/superpowers/plans/2026-09-23-fundraiser-web-app.md`):
  - integer cents
  - ISO dates and local "today"
  - `h()` only, never innerHTML
  - no `as any` / `@ts-ignore`, no empty catch
  - `confirmDialog`, never `window.confirm`
  - colour literals only in `web/src/styles/tokens.css`
  - comments explain why
  - wording plain for non-technical volunteers
- The Help guide (`web/src/ui/helpView.ts`) is keyed by `HealthId`/`Status`. New checks and user-visible features must be explained there. Keep its drift-guard test passing.
- UI tasks: do a visual pass in demo mode (`npm run dev -- --port 5176 --strictPort`, then `http://localhost:5176/?demo`) at 1280 px and 360 px, light and dark. Save screenshots to the SDD workspace's `screens/v11-*`. Stop any server you start; never touch processes you didn't start.
- Commits end with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`. Do not push.

### Task 1: Parked review fixes

**Files:** `web/src/ui/errors.ts`, `web/src/ui/table.ts` (+ CSS as needed), `web/src/ui/export.ts`, `web/src/ui/helpView.ts`, `web/src/store.ts` and any other `crypto.randomUUID` call sites, `test/ui/app.test.ts`, `test/ui/form.test.ts`, plus tests for each change.

1. **errors.ts:** on a CONFLICT whose message is not the stale-edit message ("Someone else changed this row since you opened it."), show the server's message in the confirm dialog, keeping the Reload action.
   - Test: the create-conflict text "This entry was already saved with different values. Reopen it to check." is shown.
2. **table.ts:** stop putting `role="button"`/`tabindex` on `<tr>`. For rows with `onOpen`, the first cell holds a real `<button type="button" class="row-open">` (visually it's the cell's text), which opens the row. Clicking anywhere on the row still opens it (mouse convenience). Keyboard and screen readers use the button.
   - Keep the `data-label` mobile card layout working.
   - Update the existing table tests (click, Enter/Space now go through the button) and the other view tests that rely on row clicks.
3. **export.ts:** write date columns as real Excel date cells. Use SheetJS `cellDates` or a Date object with number format `yyyy-mm-dd`, built from ISO parts in UTC so there is no timezone shift. Blank stays blank.
   - Test by reading back the generated workbook's cell type.
4. **helpView.ts:** remove the unused `SAID` entries (`typePhone`, `notCountedPreview`, `lookupDuplicate`), or quote them in the text. Keep the drift-guard test meaningful.
5. **Test hygiene:** `test/ui/app.test.ts` must remove listeners / restore `document.visibilityState` after each test. `test/ui/form.test.ts` must restore `Element.prototype.scrollIntoView`.
6. **UUID fallback:** a `newId()` helper that uses `crypto.randomUUID` when available, otherwise builds an RFC 4122 v4 id from `crypto.getRandomValues`. Use it everywhere `randomUUID` is called in `web/src`.
   - Test with `randomUUID` stubbed away: the result matches the UUID regex the server enforces.

### Task 2: "Possible duplicate payments" health check

**Files:** `web/src/engine/constants.ts`, `web/src/engine/summary.ts`, `web/src/ui/helpView.ts`, `test/engine/summary.test.ts`, and the parity test only if its health mapping needs an explicit exclusion.

- New `HealthId` `possibleDuplicatePayments`. Label: `Possible duplicate payments` (target `payments`).
- Rule: payments with a non-empty match key, a non-blank date and a non-null amount, where more than one payment shares the same (key, amount in cents, date). Every payment in such a group is listed.
- The Summary Data-health intro says every figure should read 0. Keep that sentence, but for this item the Help text explains "two real installments of the same amount on the same day are possible — check, it may be fine".
- The existing Summary UI renders it automatically (`healthItem`). Check the Show link filters the Payments view.
- Tests:
  - a duplicate group is flagged
  - a different date, amount or phone is not flagged
  - a blank date is not flagged
  - phones spelled differently but with the same match key are flagged
  - the parity test stays green

### Task 3: Log a payment from a donor

**Files:** `web/src/ui/paymentForm.ts`, `web/src/ui/pledgeForm.ts`, `web/src/ui/pledgesView.ts`, `web/src/ui/lookupView.ts` (and `app.ts` if the lookup view needs store and error-reporter deps), plus tests.

- Add `phone?: string` to `PaymentFormOptions`, used as the default phone for a new payment. The donor preview must already show the donor on open.
- Pledge edit dialog: a secondary "Log a payment" button. It is shown only for an existing pledge with a phone, and opens the payment form pre-filled once the pledge dialog closes. Don't stack two form dialogs.
- Donor card in Find donor: a "Log a payment" button, same behaviour. Saving goes through `store.savePayment` with the per-form `newId`, like `paymentsView`.
- Tests:
  - pre-filled phone and preview
  - the button is absent for a phoneless pledge
  - saving from the donor card calls `store.savePayment` with the phone

### Task 4: Pledge status filter, "Needs follow-up", and payment date range

**Files:** `web/src/ui/pledgesView.ts`, `web/src/ui/paymentsView.ts`, `web/src/ui/filter.ts` (extend if needed), a new pure helper module for follow-up selection (e.g. `web/src/engine/followUp.ts`), CSS, plus tests.

- **Pledges:** a row of toggle chips: All · Pending · Partial · Paid · Overpaid · **Needs follow-up**.
  - "Needs follow-up": status Pending or Partial, with the latest of `lastPaymentDate` or `datePledged` more than 30 days before today (or both blank). Sorted by balance, largest first, unless the user picks a column sort.
  - Chips combine with search and with a Data-health `ListFilter` (AND).
  - State persists in the view closure, like `query`/`sort`.
  - Chips are keyboard accessible (`aria-pressed`).
- **Payments:** From / To date inputs (inclusive; either may be blank) combined with search and the health filter. Undated payments are hidden when any date bound is set. A "Clear dates" control.
- The totals bands stay the overall totals. Add a small "Showing N of M" line when any filter is active.
- Tests: the follow-up helper at the 30-day boundary with a fixed today; chips; the date range; combination with search.

### Task 5: Friday display mode

**Files:** `web/src/auth.ts` (new non-prompting `hasFreshToken(): boolean`), `web/src/ui/app.ts` (route + mode), a new `web/src/ui/displayView.ts`, CSS, plus tests (`test/auth.test.ts`, `test/ui/display.test.ts`).

- Entry: route `#display`, and `?display=friday` in the URL is treated the same (DESIGN.md). A "Friday display" link sits on Summary near Download.
- Layout: full screen, no nav bar, no tabs, no offline banner. A centred stack: eyebrow ("Islamic Center of Greensboro"), display title (the campaign name; default "Fundraiser"), progress bar, "$X raised of $Y", the percentage, and "N donors have pledged".
  - Use `clamp()` sizes with existing tokens only.
  - No names, phones or amounts per donor.
  - Inherits the theme.
  - A small "Exit" link (to Summary) in a corner.
- Refresh: every 3 minutes while the page is visible, call `store.load()` **only if `auth.hasFreshToken()`**. Display mode must never call `getToken`/`refreshIfStale` or open the sign-in dialog.
  - Show "Updated hh:mm" (local time).
  - If more than 15 minutes have passed since the last successful load, show a subtle "Figures may be out of date — tap to reconnect". Tapping it calls the normal refresh, which may prompt: that is user-initiated.
  - Leaving display mode clears all timers and listeners.
- Tests:
  - `hasFreshToken` true/false with a fake token
  - with a stale token, the refresh tick does not call `store.load` and no `<dialog>` opens
  - with a fresh token, it loads
  - the stale note appears after 15 minutes (fake timers)
  - no donor names appear in the DOM
  - timers are cleared on exit

### Task 6: Installable (manifest + icons, no service worker)

**Files:** `web/public/manifest.webmanifest`, `web/public/icons/*` (an ICG monogram SVG + 192/512 PNGs + `apple-touch-icon` 180 PNG), `web/index.html` (manifest link, `theme-color` meta for light and dark, apple-touch-icon link, replacing the `data:,` favicon with the SVG icon), plus a build check.

- The monogram "ICG" is in the DESIGN.md palette (ivory background, forest/gold) and generated by a script or hand-written SVG. Rasterise the PNGs with a dev-time tool, committed as files; no new runtime dependency.
- Hex colours inside the SVG/manifest are allowed (they are assets, not CSS) but must be DESIGN.md token values.
- Paths must work under the Pages base `/icg-fundraiser-tracker/`: use relative URLs in the manifest (`start_url: "."`, `scope: "."`) and Vite-processed links in index.html.
- **No service worker.**
- Verify: `npm run build`, then check `dist/manifest.webmanifest` and the icons exist and index.html references resolve with `VITE_BASE=/icg-fundraiser-tracker/`.

### Task 7: Performance check at event scale

**Files:** `web/src/demo.ts` (a `big` seed: `?demo&big` gives 1,500 pledges and 3,000 payments, deterministic), maybe `web/src/ui/table.ts`, plus tests.

- Measure with the Playwright MCP tools in demo mode at 360 px and 1280 px:
  - the time from typing one character in Pledges search to redraw completing (after the 150 ms debounce)
  - the time from a store publish (save a pledge) to redraw completing
  - Record the numbers in the report.
- **Only if** a redraw takes more than 100 ms: render tables in pages of 100 rows with a "Show more (N left)" button (`table.ts`), keeping sort and filter semantics and the mobile card layout. Add tests.
- If under budget, make no table change: record the measurements and stop.

### Task 8: CI smoke tests + housekeeping

**Files:** `package.json` (dev dependency `@playwright/test`, script `test:e2e`), `playwright.config.ts`, `e2e/*.spec.ts`, `.github/workflows/pages.yml`, `README.md`.

- The e2e suite runs against `vite preview` of a demo-capable build.
  - Demo mode is DEV-only, so run e2e against the Vite dev server started by Playwright's `webServer` on a free port. Do not ship demo code in production builds.
- Specs, each short and deterministic:
  - add a pledge
  - log a payment from the donor card
  - the Pledges "Needs follow-up" chip
  - the Payments date range
  - display mode shows totals and no names
  - no horizontal overflow at 360 px on each tab
- Workflow:
  - a separate `e2e` job on `pull_request` and `push` with `continue-on-error: true` on push to main, so it never blocks deploys
  - install Chromium only
  - upload the Playwright report on failure
- Pin all jobs to `runs-on: ubuntu-24.04`.
- README: note Node ≥ 22.22 (the jsdom engine requirement) and how to run `npm run test:e2e`.
- `npm run check` stays unit-only; e2e is separate.
